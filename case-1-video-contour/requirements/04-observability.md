# ТЗ: наблюдаемость видеоконтура

[← к кейсу](../README.md)

Постановка задачи на наблюдаемость видеоконтура: пользовательские метрики, очередь обработки, расход ресурсов,
алерты и эксплуатационная приёмка. События маршрута содержат клуб, рецепт, код ответа и длительность без подписей.
Пульс воркера отправляется раз в минуту. Контролируются PENDING и зависшие RUNNING-задачи.

## Требования

### 1. Метрики

| ID | Метрика | Откуда | Разрез | Зачем |
|---|---|---|---|---|
| OBS-1 | Время до первого кадра (от открытия рецепта до первого кадра; запуск кнопкой Play — отдельная метрика) | плеер в браузере | клуб, площадка (сайт, Telegram, Max), качество старта | NFR-1, быстрый старт |
| OBS-2 | Доля времени буферизации, число остановок на просмотр | плеер | клуб, площадка | NFR-2, качество под канал |
| OBS-3 | Ошибки плеера по типу: сеть, 401, 403, 404, разбор плейлиста | плеер | клуб, площадка | видеть отказы |
| OBS-4 | Перезапросы плейлиста после 403: успешные и отказанные | плеер и маршрут | клуб | бесшовный просмотр работает; рост отказов — признак проблемы права или часов |
| OBS-5 | Ответы маршрута плейлистов по коду (200 / 401 / 403 / 404 / 429 / 502) и время ответа p50 / p95 | маршрут | файл (мастер, качество), cache hit/miss | NFR-3, сбой хранилища, атака перебором |
| OBS-6 | Попадания в кэш плейлистов | маршрут | — | скорость старта, работа Redis |
| OBS-7 | Очередь нарезки: число задач `PENDING`, возраст самой старой, `FAILED` за сутки, длительность нарезки на минуту видео, время от принятия загрузки до DONE | база и воркер | среда | NFR-4, замер допущения A6 |
| OBS-8 | Трафик из хранилища показа за месяц | отчёт провайдера хранилища | бакет, клуб по префиксу | порог CDN 50 ГБ в месяц |
| OBS-9 | Объём хранилищ по классам и рост за месяц | провайдер | бакет | затраты, тарифы по медиа-лимитам |
| OBS-10 | Досмотр видео (доля просмотренного) | плеер | рецепт, клуб | продуктовая метрика из PRD для аналитики автора |

Требования к клиентским метрикам: без персональных данных (идентификатор пользователя не передаётся, только клуб, рецепт,
площадка и тип устройства); выборка, а не каждый просмотр, если объём станет заметным; отправка не должна задерживать плеер.

### 2. Алерты

Канал — существующий Telegram-бот алертов владельца. Пороги — стартовые, уточняются после двух недель базовой линии.

| ID | Условие | Порог | Важность | Что делать (ссылка на инструкцию) |
|---|---|---|---|---|
| ALR-1 | Самая старая задача нарезки в `PENDING` | старше 30 минут | высокая | воркер жив? OPS «Видео не нарезалось» |
| ALR-2 | Задачи нарезки `FAILED` | ≥ 1 за час | средняя | текст ошибки в задаче; повтор из редактора |
| ALR-3 | Воркер нарезки не подаёт пульс | нет пульса 10 минут | высокая | перезапуск контейнера |
| ALR-4 | Доля 404 / 502 маршрута плейлистов | > 1 % ответов за 15 минут, минимум 20 запросов | высокая | лог `WARN playlist object missing` даёт ключ объекта |
| ALR-5 | Время ответа маршрута p95 | > 1 с 15 минут | средняя | хранилище или Redis (TD #104, #212) |
| ALR-6 | Время до первого кадра p95 | > 4 с за час | средняя | сравнить по площадкам и клубам |
| ALR-7 | Проверочная матрица доступа (по расписанию, а не вручную) | любая проверка не совпала с ожидаемым | **критическая** | публичный префикс закрыт → видео не играет; закрытый префикс открыт → утечка платного контента |
| ALR-8 | Трафик из хранилища | 80 % порога CDN за месяц | информационная | решение о подключении CDN |
| ALR-9 | Всплеск 429 у одного временного корреляционного ключа | > 5 раз за час | информационная | признак массового скачивания |

### 3. Логи

Обязательный состав строки события маршрута плейлистов и воркера нарезки:

| Поле | Пример | Правило |
|---|---|---|
| время, уровень, модуль | `WARN [media/hls]` | уровень явным словом, чтобы искать по нему |
| клуб, рецепт | `clubId`, `recipeId` | всегда |
| ключ объекта | `clubs/…/media/hls/…/master.m3u8` | ключ — не секрет, писать можно |
| код ответа, длительность | `404`, `370 ms` | всегда |
| задача нарезки | `jobId`, попытка, длительность | для воркера |
| **запрещено** | подписи, ссылки с `X-Amz-`, ключи доступа, e-mail, идентификатор пользователя в открытом виде | проверяется тестом, по контракту |

### 4. Дашборд «Видео»

Одна страница: старт и буферизация по площадкам; ответы маршрута по кодам; очередь нарезки; трафик и объём хранилища
против порога CDN; последние алерты. Дашборд получает агрегированные метрики из хранилища наблюдаемости.

Проверка доступа выполняется каждые 5 минут в изолированном бакете. Алерты группируются по среде и причине;
повторное уведомление — через 30 минут, закрытие — после двух нормальных интервалов. Отсутствие данных более 10 минут
вызывает отдельное уведомление. Корреляционный ключ лимитера доступен только оператору и живёт не более часа;
он не включается в клиентские метрики. Доля досмотра — длительность уникальных просмотренных интервалов / длительность
видео; повторы и перемотка не увеличивают её выше 100 %. Буферизация считается по формуле NFR-2.


## Приёмка

1. Остановленный воркер нарезки вызывает ALR-3 не позже чем через 10 минут, а загруженное в это время видео — ALR-1 через 30 минут.
2. Удалённый объект плейлиста в изолированном тестовом бакете при 20 запросах за 15 минут вызывает ALR-4; в алерте есть ключ объекта.
3. Закрытие публичного префикса в изолированном тестовом бакете вызывает ALR-7 при ближайшем прогоне.
4. На дашборде видно время до первого кадра отдельно для сайта и для встроенного браузера Telegram.
5. В логах и метриках нет подписей и идентификаторов пользователей — проверка поиском по выгрузке за сутки.

6. Для каждого OBS-1…10 подать контрольные события и сверить агрегат с расчётом; для ALR-1…9 проверить порог,
   отсутствие срабатывания ниже порога, повтор, закрытие и отсутствие данных. Контроль очереди включает зависший RUNNING.
7. Убедиться, что мониторинг свежести резервной копии уведомляет при возрасте более 24 часов.

## Вне задачи

Трассировка запросов между сервисами, хранение логов дольше текущего срока, мониторинг сервера в целом (диск, память,
процессор — частично есть отдельно).
