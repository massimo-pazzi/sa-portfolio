# Требования к видеоконтуру (выдержки)

Требования к видеоконтуру облачной платформы Су-Шеф, на которой авторы кулинарного контента могут запустить свой закрытый клуб по подписке и монетизировать кулинарный контент.

[← к кейсу](../README.md)

## Бизнес-требования

| ID | Бизнес-требование | Бизнес-обоснование |
|---|---|---|
| BR-1 | Видеорецепт начинает воспроизведение по порогу NFR-1 после открытия, без ожидания загрузки всей страницы рецепта | Удержание внимания. Мгновенный старт визуального контента захватывает внимание сразу, подтверждая релевантность страницы |
| BR-2 | Видео адаптируется к изменению канала с долей буферизации по NFR-2 | Обеспечить надежность сервиса в реальных жизненных сценариях. Если видео «зависло» в момент, когда у пользователя на сковороде горит лук, это вызывает сильнейшее раздражение и отказ от приложения |
| BR-3 | Платное видео и фото шагов получает только тот, у кого есть право | Соблюдение юридических обязательств перед авторами |
| BR-4 | Подписчик может смотреть видео по шагам приготовления | В процессе готовки пользователи взаимодействуют с рецептом дискретно (от этапа к этапу), а не смотрят ролик целиком. Избавление пользователя от ручной перемотки у плиты повышает удобство использования и формирует дополнительную ценность платной подписки |
| BR-5 | Клуб открывается и видео играет внутри Telegram и Max | Аудитория авторов живёт в мессенджерах, Необходимость переходить на внешние ресурсы для просмотра контента создает барьер для пользователей и ведет к потере трафика. Работа приложения внутри привычного мессенджера обеспечивает бесшовный пользовательский путь от поста в канале до оплаты и просмотра рецепта |
| BR-6 | Видеорецепт автора восстанавливается из защищённого резерва при компрометации сервера | Видеоконтент является главным активом авторов и основой монетизации клуба. Потеря уникальных материалов из-за взлома или действий злоумышленников может привести к остановке бизнеса, репутационному краху и судебным искам от правообладателей |
| BR-7 | Обеспечить эластичность расходов на хранение и раздачу видео пропорционально росту активной аудитории | Фиксированные затраты на простаивающие серверы при низкой нагрузке сделают экономику убыточной. Оплата строго за фактическое использование позволяет поддерживать положительную юнит-экономику с первого дня и масштабировать расходы только при наличии платящей аудитории |

## Функциональные требования

Ниже приведены выдержки из спецификации проектного решения. Идентификаторы сохраняются для связи с моделями и проверками.

| ID | Требование | BR |
|---|---|---|
| FR-1 | Обеспечить старт видеорецепта по NFR-1 и доступность ключевой текстовой информации (состав, шаги, КБЖУ) при открытии страницы рецепта, не дожидаясь полной загрузки второстепенных разделов страницы | BR-1 |
| FR-2 | Система должна кешировать данные карточек рецептов для ускорения отдачи контента пользователям. При любом создании, изменении или удалении контента через админ-панель система должна автоматически инвалидировать соответствующий кеш, гарантируя, что при первом же последующем обращении пользователи получат обновленную версию данных | BR-1 |
| FR-3 | После загрузки исходного видеофайла в панель управления система должна запускать его асинхронную (фоновую) конвертацию в формат адаптивного стриминга HLS с профилями до 1080p (Full HD), 720p (HD) и 480p (SD); профиль выше разрешения исходника не создаётся, ориентация и пропорции сохраняются | BR-2 |
| FR-4 | Процесс транскодирования не должен блокировать публикацию рецепта. Если рецепт опубликован до завершения фоновой нарезки HLS, система должна отдавать пользователям исходный загруженный видеофайл, а после успешного окончания транскодирования — автоматически переключать отдачу на адаптивный HLS-поток | BR-2 |
| FR-5 | По умолчанию видеоплеер должен автоматически переключать профиль качества воспроизводимого HLS-потока (между 1080p, 720p и 480p) в режиме реального времени в зависимости от текущей пропускной способности интернет-канала пользователя. Дополнительно в интерфейсе плеера должна быть предусмотрена возможность ручного выбора конкретного разрешения (либо возврата в режим «Авто») | BR-2 |
| FR-6 | Выдача плейлистов (.m3u8) для платных видеорецептов должна осуществляться исключительно через защищенный маршрут (эндпоинт) бэкенда приложения, исключая прямой доступ к файлам плейлистов в хранилище. При каждом запросе плейлиста система должна проверять валидность пользовательской сессии и наличие действующего права доступа (уровня REGISTERED для участника клуба либо активной подписки для PRO; автор своего клуба и администратор имеют доступ по роли) к запрашиваемому рецепту. При отсутствии прав, невалидной сессии или возникновении любой технической ошибки в процессе проверки система должна блокировать выдачу плейлиста ; отсутствие сессии возвращает 401, отсутствие права — 403, технический отказ — 5xx без выдачи медиа | BR-3 |
| FR-11 | Обеспечить возможность ознакомления неавторизованных пользователей и пользователей без подписки с базовой информацией платного рецепта и стимулировать их к оформлению подписки непосредственно на экране рецепта, исключив при этом любую техническую возможность доступа к платному контенту | BR-3 |
| FR-7 | При кешировании данных страниц рецептов в общий кеш приложения должны сохраняться исключительно статические данные и неподписанные (внутренние) пути к медиафайлам. Сохранение сгенерированных подписанных ссылок с токенами доступа в общий кеш категорически запрещено. Генерация индивидуальной подписи (токена и TTL) для платных медиафайлов должна выполняться динамически на стороне бэкенда при каждом конкретном запросе авторизованного пользователя, имеющего действующее право доступа | BR-3 |
| FR-8 | При истечении срока действия (TTL) подписанных ссылок на видеосегменты (например, после длительной паузы в процессе готовки) видеоплеер должен в фоновом режиме автоматически перезапросить обновленный плейлист через защищенный маршрут приложения, не прерывая интерфейс экрана и не требуя действий от пользователя. | BR-3, BR-2 |
| FR-12 | В режиме пошаговой готовки видеоплеер должен воспроизводить строго временной отрезок видеорецепта (от стартового до конечного таймкода), привязанный к текущему открытому шагу приготовления. По достижении конечного таймкода фрагмента воспроизведение должно автоматически останавливаться. В интерфейсе плеера должна отображаться кнопка повторного запуска текущего фрагмента с его начального таймкода. | BR-4 |
| FR-9 | В режиме пошаговой готовки пользователь должен иметь возможность переключаться на предыдущий и следующий этап приготовления двумя способами: нажатием на экранные кнопки навигации («Назад» / «Вперед») и с помощью горизонтальных жестов смахивания (свайпов влево и вправо). При переходе на другой шаг система должна обновлять текстовое описание этапа и автоматически запускать воспроизведение видеофрагмента нового шага с его начального таймкода. | BR-4 |
| FR-10 | В режиме пошаговой готовки система должна ограничивать навигацию рамками списка шагов текущего рецепта:	на первом шаге приготовления кнопка перехода «Назад» должна быть заблокирована (неактивна), а жест свайпа вправо не должен выполнять переход; на последнем шаге приготовления кнопка перехода «Вперед» должна заменяться на кнопку «Завершить готовку» (по нажатию на которую пользователь выходит из пошагового режима и возвращается на основную страницу рецепта). | BR-4 |

### Пример критериев приёмки (FR-12)

```gherkin
Сценарий 1: Воспроизведение видеофрагмента текущего шага и автоматическая остановка
 Дано: Пользователь с активной подпиской открыл рецепт в режиме пошаговой готовки на Шаге №2, которому в базе данных соответствуют таймкоды видео с 01:15 по 01:40.
 Когда: Пользователь запускает воспроизведение видео (или шаг открывается автоматически).
 Тогда:
	• Видеоплеер начинает воспроизведение строго с отметки 01:15.
	• При достижении отметки 01:40 плеер автоматически ставит видео на паузу (не переходит к воспроизведению Шага №3).
	• На экране поверх плеера отображается кнопка повторного воспроизведения («Повторить шаг»).

Сценарий 2: Повторное воспроизведение фрагмента шага по кнопке
 Дано: Видеофрагмент Шага №2 доиграл до конца (01:40) и встал на паузу, на экране отображается кнопка «Повторить шаг».
 Когда: Пользователь нажимает на кнопку «Повторить шаг».
 Тогда:
	• Видеоплеер сбрасывает позицию на стартовый таймкод текущего шага (01:15).
	• Воспроизведение фрагмента начинается заново без перезагрузки страницы и повторного запроса плейлиста (если срок действия ссылки не истек).

Сценарий 3: Защита от перемотки за пределы текущего шага (опционально, если есть таймлайн)
 Дано: Пользователь находится на Шаге №2 (таймкоды 01:15 — 01:40).
 Когда: Пользователь пытается взаимодействовать со шкалой прогресса (таймлайном) плеера.
 Тогда: Шкала прогресса отображает длительность только текущего шага (25 секунд), не позволяя случайно перемотать видео на другие этапы рецепта.
```

## Правила доставки

До готовности HLS исходник выдаётся через авторизованный маршрут приложения с поддержкой Range. Каждое чтение проверяет сессию, клуб и право; прямого URL транзитного файла у зрителя нет. После готовности HLS новые открытия используют плейлисты. Активный просмотр исходника завершается без принудительной смены источника; транзит удаляется после окончания активных чтений.

## Матрица доступа к медиа

| Актив | Аноним | Участник клуба | Подписчик клуба | Автор клуба | Админ платформы |
|---|---|---|---|---|---|
| Обложка рецепта, фото ингредиентов, лого и фото автора | да, напрямую | да | да | да | да |
| Видео рецепта уровня REGISTERED | нет (постер) | да, по подписи 15 мин | да | да | да, по подписи 6 ч |
| Видео рецепта уровня PRO | нет (постер) | нет (постер) | да, по подписи 15 мин | да | да, по подписи 6 ч |
| Фото шагов (раскрывают метод) | нет | по уровню рецепта, подпись 60 мин | да | да | да, подпись 6 ч |
| Оригинал видео | нет | нет | нет | нет, только сервер | нет, только сервер |

Автор имеет привилегию только в своём клубе. Приватный оригинал в объектном хранилище и временный файл для защищённой выдачи до HLS — разные ресурсы.

## Модель данных видео (фрагмент)

[ER-модель](../data/README.md).


| Сущность / поле | Что хранит | Кто пишет |
|---|---|---|
| `Recipe.access_level` | `REGISTERED` или `PRO` | автор в консоли |
| `Recipe.video_manifest_url` | serving URL мастер-плейлиста HLS в хранилище показа; без подписи | только воркер нарезки |
| `Recipe.image_url` / `image_original_url` | обложка (показ) и её оригинал (приватно) — два явных поля, одно из другого не выводится | маршрут загрузки |
| шаг в `Recipe.components` (JSONB) | `imageUrl` / `imageOriginalUrl` фото шага или `videoSegment {startSec, endSec}` | автор в редакторе |
| `transcode_jobs` | задача нарезки: `PENDING → RUNNING → DONE / FAILED`, число попыток, ошибка | маршрут загрузки, воркер |

Схема ключей хранилища (все ключи начинаются с клуба — заложено под мультитенантность):

```text
показ (публичные префиксы открыты, остальное по подписи):
  clubs/{clubId}/media/img/recipes/{id}/preview-{ver}.jpg          обложка, публично
  clubs/{clubId}/media/img/recipes/{id}/steps/{stepId}-{ver}.jpg   фото шага, по подписи
  clubs/{clubId}/media/hls/{recipeId}/master.m3u8 + сегменты       видео, по подписи
оригиналы (приватно, с версиями):
  clubs/{clubId}/originals/recipes/{id}/video-master.{ext}
транзит:
  tmp/{clubId}/…                                                     удаляется правилом хранилища через 7 дней
```

Версия в ключе показа (`-{ver}`) делает каждый объект неизменяемым: замена фото — новый ключ и новый URL, поэтому
кэш браузера и хранилища не нужно сбрасывать.
