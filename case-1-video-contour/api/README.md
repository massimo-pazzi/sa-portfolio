# API: маршрут плейлистов HLS видеоконтура

[← к кейсу](../README.md)

[`openapi.yaml`](openapi.yaml) — контракт маршрута видеоконтура `GET /api/media/hls/{recipeId}/{file}`
Домены, имена файлов сегментов, длительность сегмента в примере и код ошибки 429 — условные.

Что важно в контракте:

- **Маршрут отдаёт только плейлисты.** Сегменты зритель берёт из хранилища по подписанным ссылкам, которые маршрут вписывает
  в плейлист качества. Поэтому байты видео не идут через сервер приложения.
- **URL стабилен, подписи — новые на каждый запрос.** Повторный запрос того же URL — штатный способ получить свежие подписи;
  на нём же заново проверяется право.
- **401 — JSON, а не перенаправление на вход.** Маршрут исключён из общей проверки входа и проверяет сессию сам: иначе
  плеер с истёкшей сессией получил бы HTML-страницу входа вместо ошибки, которую умеет обработать.
- **Невалидный путь → 404, не 400.** Структуру путей по ответам не узнать.
- **`Cache-Control: private, no-store`.** В ответе подписи; их нельзя кэшировать.

## Контракт временной выдачи исходника

До готовности HLS плеер обращается к авторизованному маршруту исходного файла. Входные данные — идентификатор рецепта
и заголовок Range. Сессия, клуб и право проверяются при каждом чтении. Ответ: 200 для полного файла, 206 для диапазона,
416 для недопустимого диапазона; 401/403 при отсутствии сессии/права, 404 при отсутствии файла, 5xx при техническом отказе.
Заголовки: `Accept-Ranges: bytes`, `Content-Type`, `Content-Length`, для 206 — `Content-Range`, `Cache-Control: private, no-store`.
Путь транзитного файла клиенту не передаётся. После DONE новые открытия используют HLS; уже начатое чтение завершается.

## Проверка спецификации

```bash
npx @redocly/cli@1.25.11 lint openapi.yaml
npx @stoplight/prism-cli@5.12.0 mock -p 4019 openapi.yaml
```

Mock предоставляет примеры ответов для проверки клиента. Проверка прав, Range-доставка и воспроизведение
проверяются сценариями приёмки с сервером и тестовыми медиа. Примеры подписей сокращены и иллюстрируют формат.
